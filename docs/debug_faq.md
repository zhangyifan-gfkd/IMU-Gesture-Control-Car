# 调试问题速查（FAQ）

> 用法：**先看 §1 的 5 分钟定位流程**，再去对应章节查具体原因。
> 关键词索引：编译报错、串口乱码、I2C、姿态漂移、方向相反、nRF24L01、丢包、手感、复位重启。

---

## 1. 5 分钟定位流程（先分层，再查错）

所有问题的第一步都是**判断故障在哪一层**。串口输出是最快的证据。

```
① 串口有输出吗？
   没有 ────────────────► §2.1（烧录/串口问题）
   有
   ↓
② 有没有 ICM20689 ready？
   没有（ERR）──────────► §3.1（I2C 问题）
   有
   ↓
③ roll/pitch 数值是否合理？（平放时接近 0，倾斜时跟随）
   乱跳/不动/漂移 ──────► §4（姿态问题）
   合理
   ↓
④ 有没有 nRF24L01 ready？
   没有（ERR，进入 BENCH）► §5.1（SPI/供电问题）
   有
   ↓
⑤ 倾斜时 vx/vy 有没有变化？方向和大小对不对？
   不变 ────────────────► §5.3（映射参数/死区）
   方向相反 ────────────► §4.4（IMU_MOUNT / INVERT）
   正常 → 问题在车端或链路 → §5.2
```

> **一句话原则**：**永远先把 `DEBUG_LEVEL` 设成 2**（每帧输出）。看不清数据就无法定位，光靠猜会浪费一整天。

## 2. 编译与烧录

### 2.1 串口完全没输出

| 可能原因 | 判断方法 | 解决 |
| --- | --- | --- |
| USB 线只能充电 | 换一根已知能传数据的线 | 换线（最常见，占一半以上） |
| 串口选错 | Arduino IDE 工具→端口，有多个 COM 口 | 拔掉板子看哪个 COM 消失，就是它 |
| 波特率不匹配 | 串口监视器右下角 | 设 **115200** |
| 板子没进下载模式 | 上传时报 `Failed to connect` | 按住 **BOOT** → 按一下 **EN** → 松开 BOOT → 重新上传 |
| 驱动没装 | 设备管理器有黄色感叹号 | 装 CP210x 或 CH340 驱动 |
| 固件跑飞了 | 之前能跑，改了代码后不行 | 换回上一个能跑的版本对比 |

### 2.2 串口有输出但全是乱码

**只可能是波特率不对**。设成 115200。

如果波特率对了还是乱码，检查是不是把 `Serial.begin()` 写成了其他值，或者代码里有多处 `Serial.begin()`。

> 本项目串口输出全部是 ASCII 英文，所以**不存在中文乱码问题**。看到乱码就是波特率问题。

### 2.3 编译报 `RF24.h: No such file or directory`

没装 RF24 库。Arduino IDE → 工具 → 管理库 → 搜索 **RF24** → 选作者 **TMRh20** 的那个 → 安装。

> 注意：不要装成 `RF24Network` 或 `nrf24L01`（另一个作者的库），接口不一样。

### 2.4 编译报 `ESP32 Dev Module` 相关错误

开发板类型没选。工具 → 开发板 → ESP32 Arduino → **ESP32 Dev Module**。

如果菜单里没有 ESP32 系列，说明没装 ESP32 开发板包：首选项 → 附加开发板管理器网址填
`https://espressif.github.io/arduino-esp32/package_esp32_index.json`，然后在开发板管理器里装 `esp32`。

### 2.5 上传时报 `Timed out waiting for packet header`

按住 BOOT 键不放，点上传，看到 `Connecting...` 时松开。这是 ESP32 自动下载电路不灵敏的经典问题。

### 2.6 `Sketch too big` / `text section exceeds available space`

分区表不够。工具 → Partition Scheme → 选 **Huge APP (3MB No OTA)**。

## 3. I2C 与 ICM20689

### 3.1 串口打印 `ERR ICM20689 init failed`

固件会同时打印实际读到的 `WHO_AM_I`，**先看这个值再动手**——它直接告诉你是哪一类问题：

```
ERR  ICM20689 init failed (WHO_AM_I=0x00, expect 0x98)
```

| 顺序 | 检查 | 方法 | 通过判据 |
| --- | --- | --- | --- |
| 1 | 供电 | 万用表直流电压档，红表笔 VCC、黑表笔 GND | 3.25~3.35V |
| 2 | 共地 | 万用表通断档，ESP32 GND 到 IMU GND | 蜂鸣 |
| 3 | **CS 是否拉高** | 通断档量 CS 到 3V3 | 蜂鸣。**ICM20689 靠 CS 电平选择接口，CS 悬空 = I2C 无应答** |
| 4 | SDA/SCL 是否接反 | 对调这两根线再试 | 打印 OK |
| 5 | SDO/AD0 是否接地 | 通断档量 SDO/AD0 到 GND | 蜂鸣（否则地址变成 0x69） |
| 6 | 模块是否虚焊 | 轻压模块看串口是否偶尔恢复 | 稳定 |
| 7 | 模块是否损坏 | 换一块 ICM20689 | 打印 OK |

**为什么先量电压**：三分之一的"初始化失败"是面包板某个孔坏了或者线断了，导致模块根本没上电。这个检查只需 10 秒。

**为什么 CS 排第 3**：这是 ICM20689 与 MPU6050 最大的接线差异。MPU6050 会自动识别接口，CS 悬空也能走 I2C；ICM20689 不会——**CS 悬空时它老老实实等 SPI 时钟，I2C 一直没应答**，而现象和"模块坏了"完全一样，极易误判。

### 3.2 `WHO_AM_I` 返回奇怪的值

ICM20689 的 `WHO_AM_I`(0x75) **固定返回 `0x98`（十进制 152）**。

| 返回 | 含义 | 处理 |
| --- | --- | --- |
| `0x98` | **正品 ICM20689** | 正常 |
| `0x68` | 这是 MPU6050，不是 ICM20689 | 模块拿错了；或代码里 `IMU_WHO_AM_I_EXPECT` 被改过 |
| `0x70` / `0x71` | MPU6500 / MPU9250 兼容片 | 不是本项目器件，灵敏度/噪声特性不同，建议换货 |
| `0x00` | I2C 完全没通 | 查 §3.1（优先查 CS 和供电） |
| `0xFF` | 总线被拉高（没设备或上拉异常） | 查接线 |
| `0x12` | ICM20602 | 寄存器布局相近但不是 ICM20689，需自行核对手册 |
| 其他 | 非 ICM20689 系列 | 换模块 |

> 固件里这一行是**严格比对**（`id != 0x98` 就失败），不像兼容写法那样放行多个 ID。这是刻意的：**先确认器件型号对，再谈精度**，比"能跑就行"省下后面大量排查时间。

### 3.3 能初始化，但数据一直不变

- **I2C 速度太快 + 线太长**：把代码里 `Wire.begin(21, 22, 400000)` 的 `400000` 改成 `100000`。
- **模块处于休眠**：`PWR_MGMT_1` 没写成功。代码里已有回读校验，若仍如此，说明 I2C 有间歇性故障 → 换线。

### 3.4 数据偶尔跳成 -32768 或超大值

这是 I2C 读失败的典型表现（读到全 0 或全 1）。检查：
1. 线材是否过长（> 30cm 且未绞线）
2. 附近是否有电机/舵机在动作（电机换向会产生强干扰）
3. 电源是否与电机共用（**必须分开供电**）

> 代码里 `imuRead()` 已经检查了 `requestFrom` 的返回值，读失败会返回 `false` 并跳过本帧。如果串口里频繁出现 `ARMED` 位跳动但角度为 0，可能是频繁读失败。

### 3.5 能初始化、也能用，但姿态明显更抖（加速度 DLPF 没设）

**这是 ICM20689 最隐蔽的一个坑，也是从 MPU6050 迁过来时必踩的**：

| 器件 | 加速度数字低通在哪 |
| --- | --- |
| MPU6050 | `CONFIG`(0x1A) 的 `DLPF_CFG`，**陀螺和加速度共用一个** |
| **ICM20689** | 陀螺在 `CONFIG`(0x1A)；**加速度在 `ACCEL_CONFIG2`(0x1D)**，是独立寄存器 |

如果只照着 MPU6050 的经验写 `CONFIG = 0x03`，结果是：陀螺低通到 41Hz 了，**加速度却还是 218Hz 宽带**——高频噪声直接进 Mahony 的比例项，表现为静止时 roll 抖动 ±1~2°、动起来角度发飘。

**判断方法**：读回 `ACCEL_CONFIG2`，`(值 & 0x07)` 应该等于 `0x03`（44.8Hz）。固件里已把这条写进 `imuInit()` 的回读校验，写不进去会直接初始化失败。

**顺带一提**：`PWR_MGMT_2`(0x6C) 也要显式写 `0x00` 使能六轴，不能假设复位默认值一定是全开。

## 4. 姿态解算

### 4.1 静止时 roll/pitch 一直在漂（慢慢变大）

| 原因 | 判断 | 解决 |
| --- | --- | --- |
| 零偏没标定好 | 看 `CAL gyro_bias` 数值，是否 > 5°/s | 重新上电，手放稳，重标定 |
| 标定时手在动 | 标定 2 秒内手抖了 | 把手放桌上再上电 |
| `MAHONY_TWO_KI` 太大 | 漂移伴随小幅振荡 | 从 0.01 降到 0.005 或 0 |
| 芯片温度漂移 | 运行 10 分钟后开始漂 | 正常现象，6 轴 IMU 的固有问题；重新长按标定 |
| 模块虚焊 | 轻压模块数据突变 | 补焊或换模块 |

**诊断技巧**：把 `MAHONY_TWO_KI` 设成 0（关掉积分），如果漂移消失，说明是积分项在"帮倒忙"（通常因为加速度噪声大）。

### 4.2 平放时 roll 不是 0

**这不一定算错**。`rollRel/pitchRel` 是相对**上电水平基准**的，如果上电时手就是歪的，那 0° 就在歪的位置。

判断方法：重新上电，这次确保平放，看 `level_ref` 是否接近 0。若 `level_ref` 本身很大（如 20°），说明上电时手没放平。

### 4.3 倾斜角度不准（和量角器比对差 5° 以上）

| 原因 | 解决 |
| --- | --- |
| 量程设错 | 确认 `GYRO_CONFIG=0x08`（±500）、`ACCEL_CONFIG=0x08`（±4g），与代码常量 `8192.0f` / `65.5f` 一致 |
| 加速度未归一化/有初值误差 | 检查 `mahonyInitFromAccel` 是否被正确调用 |
| IMU_MOUNT 选错（部分轴反向） | 换预设值逐个试 |
| 模块安装不垂直于理论轴 | 手工修：在 `levelRoll/levelPitch` 基础上加固定偏移 |

### 4.4 方向相反（前倾车后退、右倾车左移）

**不要改算法**，只改宏：

```cpp
#define VX_INVERT    (-1)   // 前倾车后退 → 改成 -1
#define VY_INVERT    (-1)   // 右倾车左移 → 改成 -1
#define TILT_INVERT  (-1)   // 云台俯仰反向
#define PAN_INVERT   (-1)   // 云台水平反向
```

**先试 `IMU_MOUNT`（0/1/2/3 四个预设），再试 `*_INVERT`**。因为 `IMU_MOUNT` 错会导致 roll 和 pitch 同时错，而 `*_INVERT` 只影响单个轴。

### 4.5 快速动作时角度滞后/过冲

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 明显滞后 | `MAHONY_TWO_KP` 太小 | 从 1.0 增到 1.5~2.0 |
| 快速动作后抖动几秒 | `MAHONY_TWO_KP` 太大 | 降到 0.6~0.8 |
| 剧烈甩手后角度"飞"了 | `dt` 异常大 | 检查是否有阻塞调用；`dt` 已限幅到 100ms |
| 加速时角度被"带偏" | 加速度计受线加速度干扰 | 6 轴 IMU 的固有问题；降低 `MAHONY_TWO_KP`，多依赖陀螺积分 |

## 5. 无线通信

### 5.1 串口打印 `ERR nRF24L01 init failed`

| 顺序 | 检查 | 方法 |
| --- | --- | --- |
| 1 | **VCC 电压** | 万用表量模块 VCC-GND，必须 **3.3V**（不是 5V，也不能是 0V） |
| 2 | **有没有 100µF 电容** | 没有就焊一个，这一条解决 60% 的 nRF 问题 |
| 3 | SPI 五根线 | 逐根对照 [wiring_diagram.md](wiring_diagram.md) §1.2 |
| 4 | CE/CSN 是否接反 | CE=GPIO4，CSN=GPIO5，接反了一定失败 |
| 5 | 模块本身坏 | 换一块（到手不良率 5~10%） |
| 6 | 供电能力 | 换 AMS1117-3.3 单独给 nRF 供电 |

### 5.2 初始化成功，但车端收不到

**两端配置必须逐项一致**（这是联调最高发的问题）：

| 参数 | 双方都必须一样 |
| --- | --- |
| 信道 | 76 |
| 数据速率 | 250kbps |
| 地址 | `GLV01`（5 字节，注意大小写和字节序） |
| CRC | 16 bit |
| 负载长度 | 14 字节 |

排查工具（在手套端临时加一段自测）：

```cpp
radio.printDetails();   // 打印 nRF 寄存器状态，看 CONFIG/EN_AA/RF_SETUP 是否与预期一致
```

如果 `printDetails()` 里 `RX_ADDR_P0` 和 `TX_ADDR` 不匹配你设置的地址，说明地址写入失败。

### 5.3 丢包率很高（> 5%）

| 原因 | 判断 | 解决 |
| --- | --- | --- |
| 距离太远/有遮挡 | 靠近就好 | 换 PA+LNA 版（但要配独立 3.3V 供电） |
| 天线被手/金属遮住 | 换个握法就好 | 天线朝外伸出手套边缘 |
| WiFi 干扰 | 关掉现场路由器的 2.4G 后改善 | 信道改 76 或 100 |
| 供电不稳 | 偶尔整包丢失且伴随串口重打 banner | 加电容（见 §5.4） |
| 两端速率不一致 | 完全收不到而不是偶尔丢 | 见 §5.2 |
| 面包板接触不良 | 碰一下线就好 | 焊接固定 |

### 5.4 发几包就复位（串口重新打印 banner）

**这是 nRF24L01 的经典问题**，几乎 100% 是发射瞬间掉压导致 ESP32 复位。

三步解决（按性价比排序）：

1. **在 nRF 的 VCC-GND 之间焊 100µF 电解电容**（引线 < 2cm）—— 解决大部分情况
2. **把 `RF24_PA_MAX` 改成 `RF24_PA_LOW`**（代码默认已是 LOW）
3. **单独给 nRF 供 3.3V**（AMS1117-3.3 模块 + 独立 5V 输入）

> 判断是不是这个问题的快招：**拔掉 nRF 模块**，如果不再复位，就锁定是 nRF 供电问题。

### 5.5 `write()` 返回 false

在关闭自动应答的情况下，`write()` 返回 false 通常意味着：
1. FIFO 满了（正常，丢帧即可，代码已处理）
2. 模块没配置好（检查 `radioInit()` 返回值）
3. SPI 通信失败

**不影响功能**，代码里 `FLAG_TXFAIL` 只是提示。

## 6. 控制手感

### 6.1 手不动车却在动（自己慢慢走）

| 原因 | 解决 |
| --- | --- |
| 死区太小 | `VX_DEAD_DEG` / `VY_DEAD_DEG` 从 4 增到 6~8 |
| 姿态在漂 | 见 §4.1（零偏/积分项） |
| 车端没有超时停车 | 车端必须实现 200ms 超时归零（见协议约定 §9.5） |
| 车端把 `FLAG_ARMED=0` 当"保持上一帧" | **错误**，应为"主动停车" |

### 6.2 车太迟钝，倾斜很大才动

| 原因 | 解决 |
| --- | --- |
| 死区太大 | 减小 `VX_DEAD_DEG` |
| 满量程太大 | `VX_FULL_DEG` 从 30 减到 22~25 |
| gamma 太大 | 从 1.6 降到 1.4 或 1.2 |
| 车端把 -100~100 映射到占空比时做了额外衰减 | 检查车端 `pwm = vx * k` 的 k 值 |

### 6.3 车太灵敏，轻微动作就冲出去

反向调整：增大死区、增大满量程、增大 gamma（1.6 → 2.0）。

### 6.4 左右能控制，前后不听使唤（或反之）

- 检查 `pitch` 是否被另一个模式占用：**GIMBAL 模式下 `vx` 恒为 0**，这是设计如此（见 [分层说明](IMU人体姿态控制小车%20分层说明及具体实施步骤.md) §8.4）。
- 按一下 BOOT 键看模式是否被误切到 GIMBAL。

### 6.5 云台自己慢慢转

`PAN_DEAD_DPS` 太小（默认 8°/s）。如果手静止时 `gz` 抖动超过 8°/s，就会被积分成缓慢转动。加到 15~20。

### 6.6 换个人戴就不好用

**必须重新取水平基准**：戴好后长按 BOOT 键 1.5 秒，串口打印 `BTN long press -> re-capture level reference`。

原因：每个人的手型、手套松紧、模块贴合角度不同，零点必须重设。

## 7. 电源与稳定性

### 7.1 运行几分钟后死机

| 原因 | 解决 |
| --- | --- |
| 充电宝自动断电（负载太小） | 换带"小电流模式"的充电宝，或接一个 LED 增加负载 |
| 电源线太细导致压降 | 换粗线，缩短长度 |
| 面包板接触不良发热 | 改焊接 |
| 内存泄漏（本项目无动态分配，不太可能） | — |

### 7.2 连电脑时正常，接充电宝就不行

**供电不足**。USB 口电流限制、充电宝输出能力、线材阻抗任一项不足都会导致。判断方法：在 3V3 和 GND 之间接一个 100Ω 电阻，量电压是否仍 > 3.2V。

### 7.3 电机一转，IMU 数据就乱

**地弹干扰**。手套端和车端不共电源，所以正常不会发生。如果发生了，说明：
- 手套端和车端共用了同一个电源（**不应该**）
- 或者测试时把手套端放在了电机附近（磁场干扰）

解决：分开供电，理清地线。

> 这也是为什么设计上**手套端必须独立供电**（充电宝），不能从车上引电。

## 8. 联调（手—车）

### 8.1 手套端明明在发，车端一个包都收不到

按这个顺序，每步都能排除一层：

```
手套端：串口 tx=OK 吗？
  否 → §5.4 / §5.5
  是 ↓
手套端：radio.printDetails() 里 TX_ADDR 是 GLV01 吗？
  否 → §5.2
  是 ↓
车端：radio.begin() 成功吗？（Python 侧打印）
  否 → 车端 SPI 接线/权限问题（树莓派要开 SPI，且用 sudo）
  是 ↓
车端：RX_ADDR_P0 == GLV01？payloadSize == 14？速率 250kbps？
  否 → 改车端配置
  是 ↓
车端：available() 一直 false？→ 信道不一致 → 双方都设 76
```

### 8.2 能收到包但 CRC 校验总失败

- 两端 CRC 长度不一致（一方 8bit 一方 16bit，或一方根本没配）
- **字节序理解差异**：int16 是小端，Python 用 `struct.unpack('<h', ...)` 而不是 `>h`
- 结构体对齐：确认车端是按**偏移**取值而不是按类型自动对齐

用 [分层说明](IMU人体姿态控制小车%20分层说明及具体实施步骤.md) §9.3 的测试向量验证车端 CRC 函数：

```
A5 01 05 14 F6 00 32 00 DD FF 78 00 14  →  CRC = 0xA0
```

算出来不是 A0，就是车端算法写错了。

### 8.3 车动起来像"抽搐"

- 帧率不稳：看包里 `dtMs` 是否稳定 20
- 车端 PWM 频率与舵机冲突（共用定时器）
- 车端在收到包之前用了默认值做初始化（应该是"收不到就停"）

### 8.4 云台转到极限就卡住（舵机堵转）

车端没有对 `pan_angle` 做钳位。舱机行程通常 ±90°，超出行程会堵转、发热、扫齿。

车端必须：

```python
pan_angle = max(-90.0, min(90.0, pan_angle + pan_delta / 10.0))
```

## 9. 有用的调试技巧

### 9.1 三级调试开关

```cpp
#define DEBUG_LEVEL  2     // 0=静默 1=每5帧 2=每帧
#define DEBUG_CSV    0     // 1=CSV 输出给串口绘图器
```

### 9.2 用串口绘图器看曲线

把 `DEBUG_CSV` 设成 1，打开 Arduino IDE → 工具 → 串口绘图器，能直接看到 roll/pitch/vx/vy 的实时曲线。**调死区和 gamma 时这个比看数字高效 10 倍**。

### 9.3 不用车也能验证全部手势逻辑

nRF 失败时固件进入 BENCH 模式，继续解算并打印。所以：
- 没有车 → 也能验证 T1~T6（见 [分层说明](IMU人体姿态控制小车%20分层说明及具体实施步骤.md) §10.2）
- 没有 nRF 模块 → 也能验证姿态和映射

**这是设计上刻意做的降级**，别浪费。

### 9.4 用第二块 ESP32 做接收端自测

没等车端做好之前，用另一块 ESP32 + nRF 做接收端，把收到的包原样打印出来。这能在 10 分钟内确认"发出去的是对的"，而不是等车端同学一起排查。

### 9.5 记录现象的习惯

调通一个功能就 git commit 一次，并在 commit 里写清"改了什么参数、现象如何变化"。**一周后你会非常需要这些记录**（尤其是参数试验过程，答辩时讲"我们试了 12 组参数"比"调好了"有说服力得多）。

## 10. 还没解决怎么办

1. **确认是硬件还是软件**：把同一份固件烧到另一块 ESP32 + 另一套模块，问题跟着走还是留在原地。
2. **二分法**：注释掉一半功能（比如只保留 IMU，不初始化 nRF），看问题是否消失。
3. **回到已知良好状态**：`git stash` 回退到上次能跑的版本，逐项加回改动。
4. **查数据手册**：ICM20689 的寄存器表（`RM-ICM20689`，随库附带 PDF）和 nRF24L01+ 的 Product Specification 都不长，比搜博客靠谱。
5. **带证据来讨论**：串口完整输出（截图）+ 万用表实测电压 + 你已经排除的可能性。**"它就是不工作"没法帮你**。
