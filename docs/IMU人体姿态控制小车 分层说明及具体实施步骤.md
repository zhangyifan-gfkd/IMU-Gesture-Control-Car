## 1. 系统分层与数据流

原始提纲给的是两段式描述（手套端 / 机器人端）。为了让"每个人负责哪一层、每层的输入输出是什么"说清楚，这里改成五层：

```
L1 感知层    ICM20689 200Hz 采样         → 原始 ax,ay,az / gx,gy,gz
L2 解算层    Mahony AHRS 六轴融合         → roll, pitch, gz(°/s)
L3 映射层    死区 → 非线性增益 → 限幅      → vx, vy, pan_delta, tilt
L4 传输层    14 字节定长包 + CRC-8         → 2.4G 无线帧
L5 执行层    树莓派解包 → 电机 / 云台 / 视频 → 车体运动 + 画面
```

**分层的好处**：每层可以单独测试。手在动但车不动，先看 L1/L2 的串口数据对不对；串口数据对但车不动，问题一定在 L4/L5。

### 1.1 端到端时延预算

动作捕捉类项目，"手感"最终由时延决定。设计目标 **端到端 < 60ms**：

| 环节 | 预算 | 实测手段 |
| --- | --- | --- |
| 采样 + 解算 + 映射（ESP32） | ≤ 20ms（一帧） | 包里 `dtMs` 字段 |
| 无线发送（250kbps，关 ACK） | < 2ms | nRF24 空口时间 |
| 接收 + 解包（树莓派） | < 5ms | Python 侧打时间戳 |
| 电机响应 | ≤ 20ms | 视觉观察 |

> 这就是为什么步骤 2-6 明确要求"不要阻塞等待重发"：一次自动重发（3 次 × 250ms）就能把 60ms 预算吃光。

## 3. 手套端硬件与装配

### 3.1 结构方案

```
        棉质手套（右手，背面）
               │
        ┌──────┴──────┐
        │  ICM20689   │  ← 缝在手背正中，芯片面朝手背外侧
        │  (3.3V)     │
        └──────┬──────┘
               │ I2C：SDA/SCL + CS(接 3V3) + 3V3 + GND（5 根）
        ┌──────┴──────┐
        │   ESP32     │  ← 固定在小臂内侧（腕带/魔术贴）
        │  DevKit     │
        └──────┬──────┘
               │ SPI：SCK/MISO/MOSI/CSN/CE + 3V3 + GND（7 根）
        ┌──────┴──────┐
        │ nRF24L01+   │  ← 贴在 ESP32 背面，天线朝外、远离金属和手
        └─────────────┘
```

### 3.2 三条硬约束（违反会直接导致调试失败）

| 约束 | 原因 | 正确做法 |
| --- | --- | --- |
| **nRF24L01 必须 3.3V 供电** | 芯片绝对最大电压 3.6V，5V 直接烧 | 从 ESP32 的 3V3 引脚取电；ESP32 用 5V/USB 供电 |
| **VCC-GND 之间必须有 10~100µF 电解电容** | 发射瞬间 115mA 冲击电流，无电容会电压跌落 → 复位/丢包 | 电容引脚尽量短，直接焊在模块焊盘上 |
| **天线区域不能贴金属、不能握在手里** | 2.4G 天线被遮挡时距离从 50m 掉到 1m | 天线伸出边缘朝外；别用锡箔或金属外壳 |

### 3.3 电源与功耗预算

| 器件 | 工作电流 | 峰值 |
| --- | --- | --- |
| ICM20689（六轴全开，200Hz） | ≈ 3.5 mA | — |
| nRF24L01+（PA_LOW 发射） | 15 mA | 115 mA（发射瞬间） |
| ESP32（WiFi 关闭，50Hz 单核） | ~40 mA | ~240 mA |
| LED | 5 mA | — |
| **合计** | **~65 mA** | **~360 mA** |

- **供电**：ESP32 用 USB 供电（5000mAh 充电宝可跑 10 小时以上），3V3 引脚给两个模块。
- **不要**用 9V 方块电池 + AMS1117 直接带 ESP32：9V 电池内阻大，发射瞬间就掉压。
- 若必须电池供电，选 **3.7V 锂电池 + 升压 5V 模块**，或直接用带 18650 的 ESP32 开发板。

### 3.4 装配步骤（G10）

1. **先面包板跑通，再缝进手套**。缝好才发现接线错，返工成本极高。
2. ICM20689 用双面胶 + 尼龙线缝边固定在手背；芯片面朝外，模块红线（VCC）朝指尖方向（便于套用 `IMU_MOUNT=0`）。
3. I2C 四根线 + **CS 那根线**用细硅胶线（比杜邦线软），沿手套背面走到小臂。CS 在手腕处就近接到 3V3。
4. nRF24L01 固定在腕部，天线朝小臂外侧，远离手掌（手掌会吸收 2.4G）。
5. ESP32 放小臂内侧，用魔术贴绑带固定；USB 口朝手肘方向，方便插线充电。
6. 所有焊点涂热熔胶做应力释放——**戴着手套的手会反复弯折线材**，这是断线第一大来源。
7. 装完做 10 分钟连续动作测试，观察丢包率是否突然变多（多为线材接触不良）。

### 3.5 接线

引脚分配与理由见 [wiring_diagram.md](wiring_diagram.md)。**改任何一根线，必须同步改** [IMU_Car.ino](../code/arduino/IMU_Car.ino) 第 1 节的 `PIN_*` 宏。

## 4. 坐标系与符号约定

这一节是后面所有讨论的前提，**必须和车端同学当面确认一次**。

### 4.1 三个坐标系

| 坐标系 | 定义 |
| --- | --- |
| 芯片坐标系 | ICM20689 丝印箭头方向：X 沿模块长边，Y 沿短边，Z 垂直模块向上 |
| 手套坐标系 | X = 手背朝指尖，Y = 朝拇指侧，Z = 手背朝上（手心朝下时） |
| 车体坐标系 | X = 车头前进，Y = 车体右侧，原点在车体中心 |

`IMU_MOUNT` 宏负责把芯片坐标系旋转到手套坐标系。共 4 个预设（0/1/2/3），选错的典型现象是"往前压手，车往后退"。

### 4.2 角度符号约定（务必统一）

| 量 | 正方向含义 | 对应动作 |
| --- | --- | --- |
| `roll` > 0 | 手腕向**右**倾（右手手背抬向拇指侧） | 车向右平移 `vy > 0` |
| `pitch` > 0 | 手指**下压**（前倾） | 车向前 `vx > 0` |
| `gz` > 0 | 手绕垂直轴**逆时针**转（俯视） | 云台向左 `pan_delta > 0` |
| `tilt` > 0 | 云台**向上**抬 | 舵机俯仰角减小 |

> 如果实测方向相反，**不要改代码里的算法**，只改 `VX_INVERT` / `VY_INVERT` / `TILT_INVERT` / `PAN_INVERT` 四个宏（+1 改 -1）。这样算法和文档永远保持一致。

```
   │

```

### 5.3 时间调度策略

原始提纲用 `delay(20)` 控制帧率。实际实现改用 **绝对时刻调度器**：

```cpp
s_nextMs += FRAME_MS;
if ((int32_t)(nowMs - s_nextMs) > 200) s_nextMs = nowMs + FRAME_MS;  // 卡顿后重同步
```

理由：`delay(20)` 的实际周期是 `20ms + 本帧计算耗时`，抖动会累积；而 Mahony 的 `dt` 必须真实可信，否则积分误差会表现成"角度慢慢漂"。用调度器后帧周期稳定在 20ms ±1ms。

`dt` 由 `micros()` 实测得到，并做 `[1ms, 100ms]` 限幅——防止某一帧卡死（例如串口打印阻塞）把四元数积分踹飞。

## 6. 步骤 1：上电初始化（setup 阶段，只运行一次）

> **原始要点**
> （1）ESP32 启动，初始化串口（调试打印）
> （2）I2C 初始化，初始化 MPU6050
> 设置加速度量程、陀螺仪量程，关闭休眠；
> 传感器静态校准：手套平放静止，采集若干样本，计算陀螺仪零点偏移，消除陀螺静态漂移。
> （3）SPI 初始化，初始化 nRF24L01 射频模块
> 设置收发地址、通道、发射功率、数据包长度；
> 设置为发送模式。
> 初始化 Mahony 姿态解算器：四元数初始化为 q0=1,q1=q2=q3=0。
> 初始化变量：控制量vx,vy,pan,tilt全部置 0。
> 校准关键点：上电瞬间手套必须平放不动；如果上电手是歪的，姿态初始角度就错。

> 📌 **器件订正**：原始提纲写的是 MPU6050，**实际选用的是 ICM20689**。两者的数据寄存器布局和量程灵敏度一致，所以步骤 2-1 ~ 2-8 全部不变；但初始化阶段的 `WHO_AM_I`、加速度 DLPF 寄存器、`PWR_MGMT_2` 三处必须按 ICM20689 写，详见 §6.2。

### 6.0 上电流程与"那段 3 秒"

整个初始化约 3 秒，其中 **2 秒要求手套完全静止**、**0.5 秒要求手套平放**。这两件事最容易忘，所以固件做了强制提示：

- **进入标定**：LED 常亮 + 串口打印 `CAL  keep the glove STILL and LEVEL for ~2s ...`
- **标定结束**：串口打印 `CAL  gyro_bias(dps) = ...` 与 `CAL  level_ref = ...`

### 6.1 串口初始化

```cpp
Serial.begin(115200);
```

- 波特率 115200，串口监视器里"换行符"选 `Both NL & CR`。
- 上电延时 300ms 再打印，避开 ESP32 复位时 ROM 输出的启动日志（那几行不是你的 bug）。
- **所有串口输出用 ASCII 英文**：中文在部分串口监视器/绘图器下会乱码，而且会污染 CSV 输出。

### 6.2 I2C + ICM20689 初始化

> **器件确认**：本项目实际使用的是 **ICM20689**（InvenSense 六轴，比 MPU6050 高一个档次）。
> 下面的寄存器表是 ICM20689 的，**不要照抄 MPU6050 的教程**——两者有三处关键差异，见本节末尾的对照表。

| 寄存器 | 地址 | 写入值 | 含义 |
| --- | --- | --- | --- |
| `PWR_MGMT_1` | 0x6B | `0x80` → 延时 100ms → `0x01` | 软复位后唤醒；时钟源用 X 轴陀螺 PLL（比内部 RC 稳，降低零偏漂移） |
| `PWR_MGMT_2` | 0x6C | `0x00` | **六轴全部使能**（不能假设复位默认值一定全开） |
| `SMPLRT_DIV` | 0x19 | `0x04` | 采样率 = 1kHz/(1+4) = **200Hz** |
| `CONFIG` | 0x1A | `0x03` | **陀螺**数字低通 = 41Hz |
| `ACCEL_CONFIG2` | 0x1D | `0x03` | **加速度**数字低通 = 44.8Hz —— ICM20689 的独立寄存器 |
| `GYRO_CONFIG` | 0x1B | `0x08` | 陀螺量程 **±500°/s** → 65.5 LSB/(°/s) |
| `ACCEL_CONFIG` | 0x1C | `0x08` | 加速度量程 **±4g** → 8192 LSB/g |

**为什么选这两个量程**：
- 陀螺 ±500°/s：手部快速翻转峰值约 300~400°/s，±250 会削顶，±1000 分辨率浪费 2 倍。
- 加速度 ±4g：手腕快速抖动可达 3g 以上，±2g 会削顶；而 ±8g 时 1° 倾角只对应约 1 LSB，分辨率不够。

> ICM20689 在相同量程下的灵敏度与 MPU6050 **完全一致**（16 bit 满量程均分），所以 `ACC_LSB_PER_G` / `GYRO_LSB_PER_DPS` 两个常量不用改。

**ICM20689 与 MPU6050 的三处关键差异**（换器件时必查）：

| # | 项目 | MPU6050 | **ICM20689** | 踩坑后果 |
| --- | --- | --- | --- | --- |
| ① | `WHO_AM_I`(0x75) | `0x68` | **`0x98`** | 初始化直接失败 |
| ② | 加速度 DLPF 位置 | `CONFIG`(0x1A)，与陀螺共用 | **`ACCEL_CONFIG2`(0x1D)**，独立 | 只写 CONFIG 时加速度仍是 218Hz 宽带，姿态明显更抖 |
| ③ | `PWR_MGMT_2`(0x6C) | 默认全使能 | 建议**显式写 0x00** | 某一轴恒为 0，查不出原因 |
| — | 数据寄存器 | 0x3B 起 14 字节 | **完全相同** | 无 |
| — | 量程位 | bit[4:3] | **完全相同** | 无 |
| — | I2C 地址 | AD0=0 → 0x68 | **相同**（SDO/AD0=0 → 0x68） | 无 |

**接线差异（比寄存器更容易踩）**：MPU6050 会自动识别接口，CS 悬空也能走 I2C；**ICM20689 靠 CS 电平选接口，CS 必须接 3V3**，悬空则一直等 SPI，I2C 永远无应答。详见 [wiring_diagram.md §1.1](wiring_diagram.md)。

**两个必须做的自检**（都在 `imuInit()` 里）：

1. 读 `WHO_AM_I`(0x75)，**必须是 `0x98`**。读回 `0x68` 说明手上是 MPU6050（买错了）；读回 `0x00` 说明 I2C 没通（先查 CS 和供电）。固件会把实际值打印出来。
2. **三重回读校验**：`GYRO_CONFIG` 的 `(值 & 0x18) == 0x08`、`ACCEL_CONFIG` 的 `(值 & 0x18) == 0x08`、`ACCEL_CONFIG2` 的 `(值 & 0x07) == 0x03`。写进去读不回来说明时序或供电有问题——这一步能提前抓出 90% 的接线故障。

### 6.3 陀螺零偏静态校准

```cpp
#define GYRO_CAL_SAMPLES 1000              // 1000 点 × 2ms ≈ 2 秒
gyroBias[i] = (Σ raw_i / n) / 65.5f;       // 换算成 °/s
```

- 采样 1000 点取均值即零偏。六轴 MEMS 陀螺的零偏典型值可达 ±20°/s（ICM20689 通常比 MPU6050 小，但量级相同），不扣掉的话 20°/s × 60s = 一整圈漂移，完全没法用。
- **判据**：标定完串口打印的三轴零偏，绝对值应 **< 2°/s**。若出现 > 10°/s，说明标定时手没放稳或模块虚焊，重做一次。
- 校准后所有角速度都要减零偏：`(raw/65.5 - bias) * DEG_TO_RAD`。
- 残余零偏由 Mahony 的积分项（`MAHONY_TWO_KI`）在线补偿，所以静态标定只要求"大致对"。

### 6.4 SPI + nRF24L01 初始化

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| SPI | `SPI.begin(18, 19, 23, 5)` | ESP32 VSPI 默认引脚，显式声明避免与其他库冲突 |
| 通道 | `76`（0x4C） | 信道 0~124；**必须避开 WiFi 的 1/6/11**（对应 nRF 信道约 0~22） |
| 数据速率 | `RF24_250KBPS` | 空口时间长但**灵敏度最高**，同功率下距离约是 2Mbps 的 2 倍 |
| 发射功率 | `RF24_PA_LOW` | 无外置 PA 时开 MAX 会瞬间掉压复位（见 §3.2） |
| 自动应答 | **关闭** | 关掉 ACK 后单帧 < 1ms；开 ACK + 重发会把 60ms 预算吃光 |
| 重发 | `setRetries(0,0)` | 与上一条配套 |
| 硬件 CRC | `RF24_CRC_16` | 射频层第一道校验 |
| 负载长度 | `sizeof(CtrlPacket)` = **14** | 必须等于结构体大小；写死 32 会浪费空口时间 |
| 发送地址 | `"GLV01"`（5 字节） | 与车端接收地址完全一致，否则收不到 |

**两个易错点**：

1. `isChipConnected()` 必须检查。它能区分"SPI 通但模块没插"和"地址设错/电源不足"。
2. `begin()` 之后再 `setChannel`。顺序反了参数会被 `begin()` 里的默认值覆盖。

### 6.5 Mahony 姿态解算初始化

原始提纲写"四元数初始化为 q0=1, q1=q2=q3=0"。这是**单位四元数**，等价于"认为手套一开始是完全水平的"。

**本实现有一处改进**：不直接置单位四元数，而是用**第一帧加速度算出当前倾角**再构造四元数：

```cpp
roll0  = atan2(ay, az);
pitch0 = atan2(-ax, sqrt(ay² + az²));
q = q(roll0 绕 X) ⊗ q(pitch0 绕 Y);   // yaw 置 0
```

**为什么改**：单位四元数起步时，若手套实际有 15° 倾角，Mahony 需要 2~3 秒才能把姿态"拉"回来，这段时间读数不可信。用加速度定初值后，上电第一个数据点就是准的。

**这没有削弱"上电手必须平放"的要求**——因为 §6.6 会把此刻的 roll/pitch 记录成"水平基准"，之后所有映射都用**相对角**。手歪着上电，则"歪"变成了新零点，同样会错。

### 6.6 取水平基准

标定完零偏后，再连续采 500ms（约 25 帧）姿态，把 roll/pitch 均值存为 `s_levelRoll` / `s_levelPitch`。之后所有控制都用相对角：

```cpp
rollRel  = roll  - levelRoll;
pitchRel = pitch - levelPitch;   // 平放 = 0°
```

这一步是"手感一致性"的关键：不同人戴同一只手套（握持姿态不同）、每次重新佩戴后，只要上电时平放，零点就一致。**长按按键 1.5 秒可以重新取基准**，方便换人时快速复位。

### 6.7 控制量清零与最终自检

`vx = vy = pan = tilt = 0`；然后串口打印协议自检行：

```
PKT  sizeof=14  head=0xA5
```

**如果车端看到的 sizeof 不是 14，先停下解决这个问题再联调**（漏写 `#pragma pack` 是最常见原因）。

### 6.8 步骤 1 验收清单

跑完 setup，串口应输出（顺序一致）：

```
=========================================
 IMU Gesture Car - Glove TX  v1.0.0
=========================================
OK   ICM20689 ready (id=0x98, gyro +-500dps, accel +-4g)
CAL  keep the glove STILL and LEVEL for ~2s ...
CAL  gyro_bias(dps) = +0.31 -1.24 +0.87  (n=1000)
CAL  level_ref = roll +0.42  pitch -0.18
OK   nRF24L01 ready (ch=76, 250kbps, addr=GLV01)
RUN  frame=20ms  mode=DRIVE
PKT  sizeof=14  head=0xA5
```

| 检查项 | 通过标准 |
| --- | --- |
| ICM20689 | 打印 `OK` 且 `id=0x98`（这是型号核对，不是可选项） |
| 零偏 | 三轴绝对值 < 2°/s |
| 水平基准 | 手确实平放时 \|roll\|、\|pitch\| < 2° |
| nRF24L01 | 打印 `OK`；失败时进入 BENCH 模式（仍能在串口看姿态） |
| 协议 | `sizeof=14` |

> **BENCH 模式**：射频失败时固件不 halt，而是继续跑姿态解算并打印。这样可以"在没有车的情况下"完成 G4~G7 的全部验证。

## 7. 步骤 2：主循环（loop，20ms 一帧）

> **原始要点**
> 2‑1 获取时间间隔 dt（姿态解算必须）…建议循环周期控制 20‑30ms（33‑50Hz），不要跑太快，避免 nRF24 发包过于频繁。

### 7.1 步骤 2-1：计算 dt

| 项目 | 说明 |
| --- | --- |
| 输入 | `micros()` 上次时间戳 `s_lastUs` |
| 输出 | `dt`（秒），给 Mahony 用 |
| 限幅 | `dt ∈ [0.001, 0.100]` s |
| 自检 | 包里 `dtMs` 字段应稳定在 20±2 |

**为什么必须限幅**：Mahony 的四元数积分是 `q += 0.5·q⊗ω·dt`，dt 一旦异常大（比如长按按键时阻塞了 500ms），一次积分就能把四元数推到数值发散的边缘。

### 7.2 步骤 2-2：读取原始数据 + 滤波

> **原始要点**
> 加速度原始：ax, ay, az（m/s²）／陀螺仪原始：gx, gy, gz（rad/s）
> 可选：简单滑动平均滤波，对原始数据做窗口平滑，抑制 I2C 噪声。

- 一次 I2C 突发读 **14 字节**（从 `0x3B` 起），比逐次读 6 个数据快 6 倍，且能保证六轴**同一时刻**采样。
- 单位换算：`acc_g = raw / 8192.0`，`gyro_dps = raw / 65.5`。
- **滤波只加在加速度上**（4 点滑动平均，≈80ms 窗）：

| 要不要滤波 | 理由 |
| --- | --- |
| 加速度：**要** | 加速度反映重力方向，本身慢；噪声会让 Mahony 的比例项抖动 |
| 陀螺：**不要** | 陀螺是"快信号"，滤掉的是**有效动作**，会造成相位滞后 → 手感变"肉" |

> 这是本项目最值得在答辩里讲的一个取舍：**不是所有信号都该滤波**。引入 20ms 陀螺滞后，操作者会明显感觉"车跟手不同步"，而加速度噪声只影响 0.1° 级的抖动。

### 7.3 步骤 2-3：Mahony 解算

> **原始要点**
> 输入：gx,gy,gz,ax,ay,az,dt；输出四元数，转换得到两个关键姿态角：roll（手腕左右倾斜）、pitch（手腕前后俯仰）。
> ⚠️ 6 轴 IMU 的 yaw 航向角会随时间漂移，不拿来做绝对角度，后面云台水平用陀螺角速度做相对增量。

算法五步（`mahonyUpdate()`）：

1. **归一化加速度** → 得到测量到的重力方向单位向量。
2. **估计重力方向** → 用当前四元数算出旋转矩阵第三列 `(halfvx, halfvy, halfvz)`。
3. **叉积求误差** → `error = 测量 × 估计`。误差不为零说明姿态与重力不一致。
4. **PI 反馈** → 比例项 `Kp·error` 快速纠正；积分项 `Ki·∫error` 补偿残余陀螺零偏（这就是为什么先做 §6.3 的静态标定，让积分项只需修零头）。
5. **一阶龙格库塔积分 + 归一化** 更新四元数。

参数：`Kp = 0.5`（代码里 `MAHONY_TWO_KP = 1.0`）、`Ki = 0.005`（`MAHONY_TWO_KI = 0.01`）。

| 现象 | 调整 |
| --- | --- |
| 角度跟随慢、倾斜半天才到位 | 增大 `MAHONY_TWO_KP`（如 1.5~2.0） |
| 静止时角度抖动（尤其剧烈运动后） | 减小 `MAHONY_TWO_KP` |
| 长期缓慢漂移 | 增大 `MAHONY_TWO_KI`（别超过 0.05，会振荡） |

**yaw 的处理**（呼应原始提纲的警告）：代码里 yaw 只计算不用于控制。云台水平靠 `gz` 角速度**积分成相对增量** `pan_delta` 下发，由车端累加。这样即使绝对 yaw 漂了 90°，只要"手的转动量"对，云台就一直跟手。

### 7.4 步骤 2-4：手势映射（核心算法链路）

> **原始要点**
> 输入：roll、pitch；输出：vx, vy, pan_delta, tilt
> 1. 死区过滤 2. 非线性增益映射 3. 输出限幅，钳位到 [-100, 100]

固件里就是 `mapAxis()` 一个函数，四步：

```cpp
mag = |angle| - dead;                 // ① 死区
if (mag <= 0) return 0;
s   = min(mag / (full - dead), 1.0);  // ② 归一化
out = s^gamma * 100 + 0.5;            // ③ 非线性增益 + 四舍五入
out = ±out * invert;                  // ④ 方向修正
```

参数默认值与实测曲线见 **§8**。映射结果（`MODE_DRIVE` 下）：

| 输出 | 来源 | 范围 | 语义 |
| --- | --- | --- | --- |
| `vx` | `pitchRel` | -100~100 | 前后速度（正=前进） |
| `vy` | `rollRel` | -100~100 | 左右平移（正=右移） |
| `tilt` | `pitchRel`（仅 GIMBAL 模式） | -100~100 | 云台俯仰 |
| `pan_delta` | `gz` 角速度积分 | ±300（0.1°） | 云台水平增量 |

`vx/vy/tilt/pan_delta` 全为 0 时，`flags` 的 `FLAG_ARMED` 位清零 → 车端据此判断"操作者松手了，应该停车"。

### 7.5 步骤 2-5：组包

> **原始要点**
> 2‑5 组包：封装发送结构体

完整字段表见 **§9.2**。要点：

- `#pragma pack(push,1)` 强制 1 字节对齐。**它在这里是一道保险，不是"救命符"**：本结构体的字段顺序恰好天然对齐，实测加不加 pack 都是 14 字节。保留它是因为——① 以后调整字段顺序或新增字段就可能冒出填充字节；② 不同编译器/目标的默认对齐规则不保证一致；③ 配合 `static_assert(sizeof(CtrlPacket) == 14)` 把这个契约固化下来，改坏了直接编译不通过。
- `seq` 每帧 +1，车端据此算丢包率。
- CRC-8 覆盖前 13 字节。

### 7.6 步骤 2-6：发送

> **原始要点**
> 将结构体送入 nRF24 发送缓冲区；执行发送；读取发送状态，失败可以丢弃本帧，不阻塞循环。
> 不要阻塞等待重发，动作捕捉追求低延迟，丢一帧影响远大于卡顿。

```cpp
bool txOk = s_radio.write(&pkt, sizeof(pkt));   // 关 ACK 后 < 1ms 返回
if (!txOk && s_radioOk) pkt.flags |= FLAG_TXFAIL;
```

- 关闭自动应答后 `write()` 只是把包丢进 FIFO，**不等对方确认**，所以不会阻塞。
- 丢帧策略：**这一帧就不发了**。50Hz 下丢 1 帧 = 20ms，操作者感知不到；而重发 3 次 = 750ms，车会明显"卡住"。
- 发送失败只置一个状态位，供调试观察，不做任何补救。

### 7.7 步骤 2-7：调试输出

> **原始要点**
> 串口打印：原始 IMU 数据、roll/pitch、映射后的 vx/vy/pan/tilt，方便调试。

三级 `DEBUG_LEVEL`：

| 值 | 行为 | 用途 |
| --- | --- | --- |
| 0 | 静默 | 定型后跑电池测试（串口打印本身也耗时） |
| 1 | 每 5 帧一行（≈10Hz） | 日常调试 |
| 2 | 每帧一行 | 抓瞬时问题 |

`DEBUG_CSV = 1` 时切换成纯 CSV 输出，直接喂给 Arduino 串口绘图器看曲线：

```
roll,pitch,vx,vy,pan,tilt
```

正常输出示例：

```
[  125] roll=   1.24 pitch=  -0.35 | vx=   0 vy=   0 pan=   0 tilt=   0 | DRIVE  IDLE  tx=OK   imu=OK
[  130] roll=   2.10 pitch=  11.85 | vx=  20 vy=   0 pan=   0 tilt=   0 | DRIVE  ARMED tx=OK   imu=OK
[  135] roll= -15.42 pitch=   1.02 | vx=   0 vy= -26 pan=   0 tilt=   0 | DRIVE  ARMED tx=OK   imu=OK
```

### 7.8 步骤 2-8：帧率控制

> **原始要点**
> 控制整体帧率，例如 delay (20)，循环回到步骤 2-1

实现要点见 §5.3。**为什么 50Hz 而不是更高**：

| 帧率 | 问题 |
| --- | --- |
| 200Hz | 每 5ms 发一包，2.4G 空口拥塞，车端解包来不及，且滤波后信息量没增加 |
| 100Hz | 可用，但 nRF 空口占用翻倍，丢包率上升 |
| **50Hz（20ms）** | **动作捕捉的黄金区间**：人手动作主要能量在 5Hz 以下，50Hz 采样足够 |
| 30Hz | 快速甩手会明显"跳帧"，操作者感觉车不跟手 |

## 8. 手势映射与操控手感设计

### 8.1 三段式映射曲线（默认参数）

参数：`dead = 4°`、`full = 30°`、`gamma = 1.6`、`outMax = 100`

| 手腕角度 | 归一化 s | 输出 vx/vy |
| --- | --- | --- |
| 0~4° | — | **0**（死区内） |
| 5° | 0.038 | 1 |
| 6° | 0.077 | 2 |
| 8° | 0.154 | 5 |
| 10° | 0.231 | 10 |
| 12° | 0.308 | 15 |
| 15° | 0.423 | 25 |
| 18° | 0.538 | 37 |
| 22° | 0.692 | 56 |
| 26° | 0.846 | 77 |
| **30°** | 1.000 | **100** |
| >30° | 1.000 | 100（饱和） |

**三个设计意图**：

1. **死区 4°**：静止时人手自然抖动约 ±1~2°，叠加姿态解算噪声约 ±0.5°，4° 能保证"手不动车绝对不动"。
2. **非线性 gamma > 1**：小角度输出被压缩 → 微调时车走得慢；大角度输出饱满 → 甩手时车能冲起来。这就是原始提纲说的"小角度输出弱，大角度输出强"。
3. **饱和在 30°**：30° 之后输出恒为 100，避免"越歪越猛"导致失控；同时 30° 是手腕舒适极限，再大就累了。

> **注意**：因为 gamma>1，`s` 在 0 附近被强烈压缩，实际"有效死区"约等于 `dead + 1~2°`。这不是 bug，是设计——它让死区边缘过渡更柔和，不会出现"刚到 4.1° 就突然给 5% 速度"的突兀感。

### 8.2 gamma 参数对比（调参用）

固定 `dead=4, full=30`，不同 gamma 下各角度的输出：

| gamma | 5° | 8° | 10° | 15° | 25° | 30° | 手感 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1.0 | 4 | 15 | 23 | 42 | 81 | 100 | 线性，灵敏但易抖 |
| 1.4 | 1 | 7 | 13 | 30 | 74 | 100 | 偏灵敏 |
| **1.6（默认）** | **1** | **5** | **10** | **25** | **71** | **100** | **平衡** |
| 1.8 | 0 | 3 | 7 | 21 | 68 | 100 | 偏柔和 |
| 2.2 | 0 | 2 | 4 | 15 | 63 | 100 | 很柔和，大角度才动 |

### 8.3 手感调参三步法（G7）

**不要凭感觉乱调**，按这个顺序：

1. **先定死区**：戴好手套静止 60 秒，串口观察 `roll/pitch` 的波动范围。取波动峰值的 2 倍作为 `dead`（通常落在 3~5°）。
2. **再定满量程**：让操作者做"最舒服的最大动作"，读出此时角度（通常 25~35°），设为 `full`。
3. **最后调 gamma**：在 1.4 / 1.6 / 1.8 里挑一个。判据：能否**稳定地让车走直线 3 米不跑偏**、能否**精确停在指定位置**。两个都做到就定下来。

> 调参时把 `DEBUG_LEVEL` 设成 2（每帧输出），每改一次参数重新上电，**并重做一次标定**（改了 `IMU_MOUNT` 会改变零偏方向）。

### 8.4 两种运行模式

只有一个 6 轴 IMU，`pitch` 被 `vx` 和 `tilt` 抢用，所以必须分模式：

| 模式 | 触发 | `vx` | `vy` | `tilt` | `pan_delta` |
| --- | --- | --- | --- | --- | --- |
| **DRIVE（行进）** | 上电默认 | 由 pitch 映射 | 由 roll 映射 | 0（云台俯仰保持） | 默认 0（可开 `PAN_IN_DRIVE`） |
| **GIMBAL（云台）** | 短按 BOOT 键 | 0 | 0 | 由 pitch 映射 | 由 gz 积分 |

- 切换时串口打印 `BTN  mode -> GIMBAL`，包里 `FLAG_MODE_GIMBAL` 位置 1，车端据此切换行为。
- **设计取舍**：用物理按键而不是手势切模式，是因为"手势切模式"本身需要识别，会把 IMU 的复杂度和调试难度翻倍（大二阶段不划算）。想要手势切换，可留作二期优化。

### 8.5 云台水平为什么用角速度增量

见 §7.3。补充一个数值感受（`PAN_GAIN = 1.0`，`PAN_MAX_STEP_DEG = 30°/帧`）：

- 手以 100°/s 转：每帧（20ms）增量 = 100 × 0.02 × 1.0 = **2°**，云台平滑跟手。
- 手猛甩 500°/s：理论增量 10°，未触发限幅，正常。
- 若发现"手不动云台却慢慢自己转"，说明 `PAN_DEAD_DPS` 设小了：8°/s 只挡掉 8 以下的抖动，加到 15~20 即可。

## 9. 通信协议与联调契约

### 9.1 物理层参数（**必须双方完全一致**）

| 参数 | 值 | 不一致的后果 |
| --- | --- | --- |
| 频段 | 2.4GHz ISM | — |
| 信道 | 76 | 完全收不到 |
| 数据速率 | 250kbps | 收到乱码 |
| 地址 | `GLV01`（5 字节） | 完全收不到 |
| CRC 长度 | 16 bit | 收到乱码 |
| 负载长度 | 14 字节 | 截断/补零 |
| 自动应答 | 关闭 | 发送端行为差异（不影响接收） |

### 9.2 应用层包格式（14 字节，小端）

| 偏移 | 字段 | 类型 | 单位 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | `head` | uint8 | — | 固定 `0xA5`，帧同步 |
| 1 | `seq` | uint8 | — | 0~255 循环，算丢包率 |
| 2 | `flags` | uint8 | — | 见下方位定义 |
| 3 | `vx` | int8 | — | -100~100，正=前进 |
| 4 | `vy` | int8 | — | -100~100，正=右移 |
| 5 | `tilt` | int8 | — | -100~100，正=云台向上 |
| 6-7 | `panDelta` | int16 | 0.1° | 云台水平**增量**（不是绝对角） |
| 8-9 | `roll10` | int16 | 0.1° | 相对水平基准的 roll，调试用 |
| 10-11 | `pitch10` | int16 | 0.1° | 相对水平基准的 pitch，调试用 |
| 12 | `dtMs` | uint8 | ms | 本帧实际周期，查帧率 |
| 13 | `crc` | uint8 | — | 前 13 字节的 CRC-8 |

**`flags` 位定义**

| 位 | 名称 | 含义 | 车端该怎么反应 |
| --- | --- | --- | --- |
| 0 | `FLAG_ARMED` | 手势有效（有非零控制量） | 位=0 时**主动停车**，不要保持上一帧 |
| 1 | `FLAG_MODE_GIMBAL` | 云台模式 | 决定 `tilt` 是否生效 |
| 2 | `FLAG_IMU_OK` | 传感器正常 | 位=0 时忽略本帧控制量 |
| 3 | `FLAG_CALIB` | 正在标定 | 忽略本帧控制量 |
| 4 | `FLAG_TXFAIL` | 上一帧发送失败 | 只记日志，不影响控制 |

### 9.3 CRC-8 算法（两端必须一模一样）

```c
// 多项式 0x07，初值 0x00，不反转，不异或输出
uint8_t crc8(const uint8_t *data, uint8_t len) {
    uint8_t crc = 0x00;
    while (len--) {
        crc ^= *data++;
        for (uint8_t i = 0; i < 8; i++)
            crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x07) : (uint8_t)(crc << 1);
    }
    return crc;
}
```

**测试向量**（联调时用它验证车端算法）：

```
输入 13 字节:  A5 01 05 14 F6 00 32 00 DD FF 78 00 14
CRC-8 结果  :  A0
完整帧      :  A5 01 05 14 F6 00 32 00 DD FF 78 00 14 A0
```

这帧的解释：`seq=1`，`flags=0x05`（ARMED + IMU_OK），`vx=+20`，`vy=-10`，`tilt=0`，`panDelta=+50`（5.0°），`roll=-3.5°`，`pitch=+12.0°`，`dtMs=20`。

### 9.4 频率预算

| 项目 | 数值 |
| --- | --- |
| 单帧空口数据 | 14 字节负载 + 地址 + CRC ≈ 20 字节 |
| 250kbps 下单帧空口时间 | ≈ 0.9 ms |
| 50Hz 占空比 | ≈ 4.5%（信道非常空闲） |
| 理论最大帧率 | ≈ 200Hz（受 250kbps 限制） |

4.5% 的占空比说明：**还有 20 倍余量**，所以关掉自动应答完全不用担心"发不出去"，真正要担心的是"车端收不到"——那要查天线和供电。

### 9.5 与机器人端的 5 条约定（联调前逐条确认）

1. **结构体定义共用一份**：车端 Python 用 `struct.unpack('<BBBBbbBhhhBB', ...)` 或按偏移解析；**禁止各自手写字段顺序**。
2. **量纲固定**：`*10` 的字段表示 0.1°；`vx/vy/tilt` 是无量纲百分比（-100~100），由车端换算成 PWM 占空比。
3. **超时停车**：车端若 200ms（10 帧）收不到合法包，必须主动停车（`vx=vy=0`）。**这是安全底线**，不能只依赖 `FLAG_ARMED`。
4. **CRC 错误直接丢包**并计入统计；连续 20 帧 CRC 错 → 车端应停车并提示"信号丢失"。
5. **`pan_delta` 是增量**：车端自己维护 `pan_angle += pan_delta/10.0` 并钳位到舵机行程（如 ±90°），手套端不做角度累加。

## 12. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
